## Wejście

POST /api/acquisition/candidates/:id/run {expectedVersion,requestedFromStep?}; Idempotency-Key. Wrapper uruchamia natywny ProcessDefinition/manual trigger. POST /candidates/:id/resume {expectedVersion,nativeUserTaskId,resolution:identity_resolved|context_added|source_replaced|budget_extended|review_released|quality_revised,resolutionArtifactId}.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

202 {workflowId,candidateId}; active run=>409. WorkflowInstance owner lifecycle; ProcessInstance projection; candidate.current_workflow_id. Pause:{reasonCode,requiredArtifactType,nativeUserTaskId,workflowId,expectedVersion}. Resume wznawia tę samą instancję po dowodzie rozwiązania.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given graph, When workflowDefinitionDataSchema waliduje, Then każdy INVOKE_AGENT jest activityType w AUTOMATED i onResult jest obiektem.
2. Given start POST /api/agent_orchestrator/processes/:id/executions, When case ma input, Then zwraca execution/workflow ID i dochodzi do jawnego stop/review.
3. Given retry lub resume, When krok ma zapisany inputHash/output, Then brak duplikacji ukończonego artefaktu i nie ma drugiego własnego schedulera.

## Przypadek negatywny i granice

Stop needs_identity/needs_evidence/paused_budget ma powód i dozwoloną akcję; żaden event handler nie uruchamia niezależnego lifecycle.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Minimalna automatyzacja P0

P01–P04 są przygotowanym wejściem: kampania, seed, tożsamość i snapshot. Dopuszczamy uruchamiane przez operatora partie kwalifikacja → próbka → przegląd, korzystające z natywnego lifecycle oraz utrwalonych artefaktów. Minimalny graph ma prawdziwe INVOKE_AGENT, warunek braku problemu, ograniczoną korektę i native UserTask. Operator nie kopiuje treści między agentami. P13 i P14 nie wysyłają wiadomości.

Resume obsługuje review_released po hold i quality_revised po korekcie; oba wymagają istniejącego właściwego artefaktu oraz zgodności z oczekującym UserTask. Wznowienie nie tworzy drugiej WorkflowInstance.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T14.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Pokaż natywną definicję procesu, graph i jeden zatrzymany user task; pełny happy path jest odbierany oddzielnie w T25.

Zapisz w `evidence/tasks/T14.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.
