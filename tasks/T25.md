## Wynik, który oddajesz

Scalony moduł ma jedno działające demo acquisition i jeden poprawny przypadek zatrzymania.

## Przeczytaj przed zmianą

`AGENTS.md`, `docs/01-PROCESS.md` (kroki P01, P02, P03, P04, P05, P06, P07, P08, P09, P10, P11, P12, P13, P14, P15), `docs/04-ARCHITECTURE.md`, `docs/05-AGENTS.md`, `docs/06-UI-AND-OPERATIONS.md`, `contracts/`, `config/upstream.json` oraz właściwe upstream `AGENTS.md`. Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

Scalone zależności na main; fresh fixture campaign; public website live fetch; social snapshot import; operator sesja.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Pełny zapis demo:caseID,workflowID,runIDs,artifact versions,decision,local receipt; brak kontaktu z firmą.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given nowa kampania, When przechodzę od seed do approved pack i local export, Then dane widoczne w UI zgadzają się z bazą i runIDs.
2. Given dobry oryginał albo partial feed, When uruchamiam case, Then proces może zatrzymać się prawidłowo zamiast produkować wymuszoną ofertę.
3. Given druga organizacja, When próbuje odczytu źródła/eksportu, Then nie otrzymuje cudzych danych.

## Przypadek negatywny i granice

To przyszły gate integracji, nie deklaracja dzisiejszego wykonania. Fixture źródeł nie może udawać live social; UI stub nie kończy zadania.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T25.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Nagraj lub opisz kroki ze zrzutami. Jedna osoba wykonuje wspólny host/DB smoke, pozostałe nie resetują tej bazy równolegle.

Zapisz w `evidence/tasks/T25.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.
