## Kryteria odbioru

1. Given próbka zaakceptowana przez sędziego, When badamy zakup, Then pytamy o rzeczywisty kolejny krok/płatny pilotaż, nie tylko czy tekst się podoba.
2. Given brak zgody na cenę, When zapisuję wynik, Then nie oznaczam go jako win; powód i nakład klienta są jawne.

## Przypadek negatywny i granice

2 h to przygotowanie eksperymentu i instrumentu, nie obietnica odbycia 5 rozmów ani wywołania sprzedaży.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T34.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Niezależny reviewer potrafi wskazać hipotezę, obserwowalny wynik, koszt pozyskania i decyzję przy braku konwersji.

Zapisz w `evidence/tasks/T34.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara

Poza raportemMarkdown dostarcz `evidence/tasks/T34.json` z `taskId`, `taskSpecHash`, `assertions:[{criterion,passed,evidence}]`, `limitations`. Każdy `criterion` jest dokładnym tekstem jednego kryterium z manifestu. Niezależny reviewer zapisuje `evidence/tasks/T34.review.json` z `taskId`, `taskSpecHash`, `verdict`, `findings`. Format i polecenia w `docs/08-CEZAR.md`; nie wymyślaj hasha i nie podpisuj własnego review jako niezależnego.
