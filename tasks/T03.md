## Wynik, który oddajesz

Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

Auth hosta; encje T02; feature keys z architektury; expectedVersion i Idempotency-Key.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Wstrzykiwane repository, scope helper, ACL; typed errors 403/404/409. Po scaleniu T02 zaaplikuj jego migrację w hoście T01 i potwierdź dostęp do tabel modułu.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given użytkownik organizacji A, When odczytuje ID organizacji B, Then 404 bez treści, metadanych i linku eksportu.
2. Given brak wymaganej feature, When wykonuje mutację, Then 403 i zero zapisów.
3. Given body z obcym tenantId, When endpoint otrzymuje żądanie, Then scope pochodzi z auth, a sprzeczny body jest odrzucony.

## Przypadek negatywny i granice

Cache i lookups po samym UUID nie mogą pomijać scope; model nie dostaje bezpośredniego EntityManagera.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T03.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Dwa konta/organizacje: poprawny odczyt własnego case i nieudany cudzy. Zapisz status HTTP i liczbę rekordów przed/po.

Zapisz w `evidence/tasks/T03.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara

Poza raportemMarkdown dostarcz `evidence/tasks/T03.json` z `taskId`, `taskSpecHash`, `assertions:[{criterion,passed,evidence}]`, `limitations`. Każdy `criterion` jest dokładnym tekstem jednego kryterium z manifestu. Niezależny reviewer zapisuje `evidence/tasks/T03.review.json` z `taskId`, `taskSpecHash`, `verdict`, `findings`. Format i polecenia w `docs/08-CEZAR.md`; nie wymyślaj hasha i nie podpisuj własnego review jako niezależnego.
