## Wynik, który oddajesz

Prezenter i odbiorca rozumieją wartość oraz rzeczywisty zakres demo bez autora specyfikacji.

## Przeczytaj przed zmianą

`AGENTS.md`, `docs/01-PROCESS.md` (kroki P01, P11, P12, P14, P15), `docs/04-ARCHITECTURE.md`, `docs/05-AGENTS.md`, `docs/06-UI-AND-OPERATIONS.md`, `contracts/`, `config/upstream.json` oraz właściwe upstream `AGENTS.md`. Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

Odebrany pion; przygotowane 3 case; data sources modes; measured timings.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Krótki runbook 5 min+plan awaryjny replay z oznaczeniem; lista claims co live/co fixture/co jeszcze poza zakresem.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given świeży prezenter, When czyta runbook, Then uruchamia demo i wskazuje rezultat, koszt i rolę OM bez dodatkowego objaśnienia autora.
2. Given 60 sekund na proof pack, When niezależny reviewer czyta, Then wskazuje obserwację, zmianę i zakres dalszej usługi.
3. Given awaria providera, When pokazujemy replay, Then jawna etykieta zapisanego wykonania i pierwotny runId.

## Przypadek negatywny i granice

Nie obiecuj produkcyjnej sprzedaży ani gotowości klienta do zapłaty na podstawie sędziego syntetycznego.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T26.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Przeprowadź1 próbę pitchu oraz 1 test czytania; zapisz konkretne niezrozumiałe fragmenty i nanieś małe korekty runbooka.

Zapisz w `evidence/tasks/T26.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara

Poza raportemMarkdown dostarcz `evidence/tasks/T26.json` z `taskId`, `taskSpecHash`, `assertions:[{criterion,passed,evidence}]`, `limitations`. Każdy `criterion` jest dokładnym tekstem jednego kryterium z manifestu. Niezależny reviewer zapisuje `evidence/tasks/T26.review.json` z `taskId`, `taskSpecHash`, `verdict`, `findings`. Format i polecenia w `docs/08-CEZAR.md`; nie wymyślaj hasha i nie podpisuj własnego review jako niezależnego.
