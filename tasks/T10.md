## Wejście

Snapshot+IdentityDecision+cadence z kontraktów; oferta/version; company scoped context.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Input acquisition.signal_auditor i acquisition.fit_reviewer; maks. 3 obserwacje z evidenceRefs.

Obowiązkowo użyj `mapHostOfferToAgent` i `mapFitToProcessGates` z `contracts/agent-host-adapter.ts`, zgodnie z tabelą w `docs/05-AGENTS.md`. Oferta hosta `proposal` przechodzi do agenta jako `draft`, bez ceny; `id/version/status` pozostają przypięte w hostowym manifeście. `decision=fit` daje `serviceFit=yes` wyłącznie przy istniejącym problemie popartym źródłem i jawnym potwierdzeniu `offerCoversProblem=yes`. `deliveryFeasible` pochodzi osobno z konfiguracji lub decyzji operatora; `unknown` wstrzymuje próbkę. Nie wywnioskuj budżetu klienta, intencji zakupu ani powtarzalności potrzeby z samego dopasowania. `not_fit` i `unknown` zachowują uzasadnienie agenta. Nieznane fakty pozostają `unknown`; nie są domyślnym `yes`.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given partial feed, When builder tworzy prompt, Then cadence unknown jest jawne; żadna instrukcja nie sugeruje wymuszenia problemu.
2. Given jedna wadliwa publikacja, When diagnoza jest oceniana, Then wniosek dotyczy tej publikacji, nie całej firmy.
3. Given brak budżetu i intencji, When fit jest zwrócony, Then oba unknown; serviceFit=no blokuje PoC.

## Przypadek negatywny i granice

Prompt injection w źródle pozostaje cytowanym materiałem; nie zmienia oferty, zasad ani narzędzi.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T10.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Uruchom izolowane cases: słaby post, dobry post, injection; zapisz inputHash, agentId i assertions semantyczne.

Zapisz w `evidence/tasks/T10.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.
