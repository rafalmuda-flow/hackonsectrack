## Wynik, który oddajesz

Operator zaczyna pracę na jednym ekranie i rozumie stan każdego przypadku.

## Przeczytaj przed zmianą

`AGENTS.md`, `docs/01-PROCESS.md` (kroki P01, P02, P15), `docs/04-ARCHITECTURE.md`, `docs/05-AGENTS.md`, `docs/06-UI-AND-OPERATIONS.md`, `contracts/`, `config/upstream.json` oraz właściwe upstream `AGENTS.md`. Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

API contract campaign/cases; fixtures zgodne ze schema do czasu T04/T05; OM DataTable/CrudForm/apiCall.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Widok listy, formularz kampanii i seed import; loading/empty/error; widoczny fixture/live.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given lista przypadków, When otwieram ekran, Then widzę firmę, źródło, aktualny stan, powód stop i akcję następnego kroku.
2. Given błąd API, When zapisuję formularz, Then wpisane dane zostają i komunikat mówi co poprawić.
3. Given synthetic fixture, When oglądam listę, Then widzę oznaczenie demo bez czytania tooltipa.

## Przypadek negatywny i granice

Nie pokazuj score hot/warm ani purchase intent=yes bez dowodu; nie dodawaj 15 osobnych ekranów.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Poziom odbioru tej karty

Komponent działa wewnątrz hosta OM na jawnych fixtures odpowiadających dokładnie DTO. Ta karta odbiera renderowanie i interakcję, nie pełny przepływ backendu. Warstwa danych ma jeden adapter API, bez własnego business state. Podłączenie rzeczywistych endpointów i wspólny odbiór zapewnia T25 po scaleniu kart backendu. Raport nie może nazywać fixture pełną integracją.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T15.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

W przeglądarce wykonaj import, otwórz case i wywołaj controlled API error; zapisz 3 zrzuty oraz rezultat ręcznej kontroli klawiaturą.

Zapisz w `evidence/tasks/T15.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara

Poza raportemMarkdown dostarcz `evidence/tasks/T15.json` z `taskId`, `taskSpecHash`, `assertions:[{criterion,passed,evidence}]`, `limitations`. Każdy `criterion` jest dokładnym tekstem jednego kryterium z manifestu. Niezależny reviewer zapisuje `evidence/tasks/T15.review.json` z `taskId`, `taskSpecHash`, `verdict`, `findings`. Format i polecenia w `docs/08-CEZAR.md`; nie wymyślaj hasha i nie podpisuj własnego review jako niezależnego.
