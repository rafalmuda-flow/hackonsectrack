## Wynik, który oddajesz

Prawidłowa tożsamość i policzalna przerwa są wejściem diagnozy, nie opinią modelu.

Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

POST /api/acquisition/candidates/:id/identity {expectedVersion,websiteUrl,profileUrl?,evidenceIds,decision:confirm|reject|hold,reason}; command acquisition.identity.resolve. Dodatkowo SocialPost[]/newestFeedVerified; snapshotAsOf jako zegar testu.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

Company identity assessment yes/no/unknown z dowodem; wejście HTTP identity decision confirm/reject/hold to oddzielny enum. cadence assessment z datami, medianą i zakresem. Canonical cadencePolicy: minBaselinePosts=6, baselineWindowDays=90, maxSourceAgeDays=7, minimumGapDays=30, baselineMultiplier=3; wymagane newestFeedVerified=true. Wspólna domena oddziałów =>hold w MVP.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given strona firmy jawnie linkuje profil, When resolver analizuje źródło, Then yes z evidenceRef; podobna nazwa bez linku =>unknown.
2. Given co najmniej 6 postów w 90-dniowym oknie kończącym się datą najnowszego posta, newestFeedVerified=true i snapshot nie starszy niż 7 dni, When przerwa >= max(30 dni, 3 × mediana odstępów), Then wynik wskazuje długą przerwę wyłącznie w tym kanale.
3. Given feed partial lub sezonowa przerwa, When sprawdzam cadence, Then unknown lub expected_pause bez tezy o porzuceniu marketingu.

## Przypadek negatywny i granice

Post pinned nie definiuje najnowszego; ręczna korekta tożsamości wymaga powodu i unieważnia zależne artefakty.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T08.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Pokaż3fixtures: long gap, partial feed, winter seasonal pause. Wynik musi mieć liczby/daty zamiast czarnego score.

Zapisz w `evidence/tasks/T08.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.
