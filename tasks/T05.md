## Wynik, który oddajesz

Lista 3–5 seedów staje się listą przypadków ze źródłami bez duplikatów.

Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

POST /api/acquisition/campaigns/:id/candidates {companyName,websiteUrl,profileUrls,sourceRoute,seedEvidence}; jeden seed/request z osobnym Idempotency-Key. UI import 3–5 wywołuje te mutacje osobno i zbiera per-item rezultaty.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

201 nowy lub 200 istniejący {candidateId,deduplicated,identityStatus}. GET /api/acquisition/candidates?campaignId&cursor&limit<=50→{items,nextCursor}; GET /candidates/:id→detail zgodny z dokumentem 04.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given ten sam canonical website i kampania, When importuję dwukrotnie, Then jeden case i oba dowody pochodzenia.
2. Given podobna nazwa ale inna domena, When importuję, Then dwa osobne case; brak automatycznego scalenia po nazwie.
3. Given seed z portfolio, When jest zapisany, Then relationshipStatus=unverified.

## Przypadek negatywny i granice

Brak sourceUrl odrzuca konkretny rekord z przyczyną; brak wyników jest empty, błąd źródła jest error.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T05.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Importuj 3 seedów oraz duplikat ze zmienionym źródłem; pokaż 3 case i zachowane dodatkowe źródło.

Zapisz w `evidence/tasks/T05.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.
