## Wynik, który oddajesz

Operator zaczyna kampanię z limitem, trybem i jawną wersją oferty.

Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

POST /api/acquisition/campaigns {name,offerSnapshot,criteria,budgetLimitUsd}; Idempotency-Key; scope z auth. POST /campaigns/:id/activate {expectedVersion,approvedOfferVersion}.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

201 {id,version,status:'draft'}; activate → 200 campaign. Ofertę i kryteria przypina input manifest; koszt API USD oddzielnie od ceny oferty PLN.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given poprawna konfiguracja, When POST tworzy kampanię, Then zapisany rekord i odpowiedź activate zachowują tę samą wersję oferty, segment, limit i tryb.
2. Given robocza oferta proposal oraz rzeczywiste źródła, When uruchamiam research, Then mode=internal_demo i źródła zachowują sourceMode=live/import; status oferty nie zmienia ich na synthetic. Cena nie trafia do materiału handlowego.
3. Given istniejący run, When zmieni się konfiguracja kampanii, Then wejście starego runu nie zmienia się.

## Przypadek negatywny i granice

Nie wymyślaj zatwierdzonej ceny; limit<=0, brak wersji lub niewspierany adapter =>400.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T04.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Utwórz kampanię na danych syntetycznych oraz oddzielny research prawdziwej firmy z roboczą ofertą. Pokaż, że tryb internal_demo/commercial, status oferty i sourceMode fixture/live/import są niezależne.

Zapisz w `evidence/tasks/T04.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara

Poza raportemMarkdown dostarcz `evidence/tasks/T04.json` z `taskId`, `taskSpecHash`, `assertions:[{criterion,passed,evidence}]`, `limitations`. Format i polecenia w `docs/08-CEZAR.md`; nie wymyślaj hasha i nie podpisuj własnego review jako niezależnego.
