## Wynik, który oddajesz

Approve/discard/revise/defer ma audyt, kontrolę wersji i idempotencję.

## Przeczytaj przed zmianą

`AGENTS.md`, `docs/01-PROCESS.md` (kroki P12), `docs/04-ARCHITECTURE.md`, `docs/05-AGENTS.md`, `docs/06-UI-AND-OPERATIONS.md`, `contracts/`, `config/upstream.json` oraz właściwe upstream `AGENTS.md`. Jeśli kontrakt maszyny i tekst się rozjeżdża, zatrzymaj tylko tę kartę i zgłoś integratorowi konkretną różnicę; nie dodawaj alternatywnego endpointu. Współdzielony kontrakt zmienia jego właściciel przed startem równoległych kart.

## Wejście

POST /api/acquisition/candidates/:id/review {artifactId,artifactHash,expectedVersion,action:approve|revise|discard|hold,reason?,reviseFrom?:P07|P08|P09|P11}; Idempotency-Key. Actor z auth; reviews.decide command. reason jest wymagany dla revise/discard/hold; revise wymaga reviseFrom.

Scope `tenantId`, `organizationId`, `userId` pochodzi z auth hosta. Identyfikatory w URL/body są walidowane w tym scope. Daty mają format ISO8601UTC. Pole `expectedVersion` i `Idempotency-Key` są wymagane dla mutacji zgodnie ze specyfikacją API; odczyty nie zmieniają stanu.

## Wyjście i połączenie

ReviewDecision zartifact_hash i native_user_task_id, aktualny business status; native UserTask completion po poprawnym commit. Nie podmieniaj source/fact, aby przejśćgate.

Kolejny konsument czyta wyłącznie zatwierdzony kontrakt/artefakt. Nie przekazuj wykonania przez kopiowanie tekstu między terminalami ani przez CSV jako bazę. Wynik błędny/niepełny zachowuje status `error`/`unknown`, zgodnie z konkretnym schema; nie zamieniaj ich na wynik negatywny `no`.

## Kryteria odbioru

1. Given dwa kliknięcia tej samej decyzji/key, When oba docierają, Then jedna decyzja i ten samID.
2. Given stara wersja pakietu, When approve, Then 409 i aktualna wersja do przeglądu, bez cichego approve.
3. Given action=discard, When command kończy, Then ścieżka jest zakończona i zachowuje historię. revise/hold/discard wymagają powodu; revise dodatkowo wskazuje reviseFrom=P07|P08|P09|P11 i nie usuwa poprzedniego researchu.

## Przypadek negatywny i granice

Człowiek nie może zatwierdzić niepopartego faktu bez korekty artefaktu i ponownej oceny; approve nie oznacza wysłano.

Nie budujemy w tej karcie discovery całego internetu, CRM/fulfillment, publikacji ani kampanii reklamowej. P1 nie jest warunkiem odbioru P0. Dozwolone działania konkretnej karty wynikają z jej zakresu, a nie z ogólnego zakresu skilla upstream.

## Jak sprawdzić

```bash
node --import tsx --test tests/acceptance/T19.test.ts
```

Ten plik testu jest **zadaniem do dostarczenia w tej karcie**. Na początku może nie istnieć: polecenie ma wtedy zakończyć się błędem, nigdy pominąć test jako sukces. Test obejmuje powyższe kryteria na rzeczywistej implementacji. Nie pisz testu sprawdzającego jedynie własny hardcoded fixture lub istnienie tekstu w specyfikacji. Dla UI użyj przeglądarki/hosta i zachowaj ręczny odbiór opisany niżej; screenshot bez sprawdzonego zachowania nie wystarcza. Dla pełnego OM testu wymagane są host+DB i zapisany run/record; mocki są tylko pomocą developmentową. W logu podaj dokładny tryb: portable, native harness, full OM host albo integrated demo.

## Demonstracja i dowód

Zatwierdź v1, zmień na v2, spróbuj approval v1; pokaż konflikt oraz zachowaną historię.

Zapisz w `evidence/tasks/T19.md`: commit/base SHA, wersję OM, datę, polecenie, wynik i istotny fragment logu/status HTTP, identyfikator użytego fixture, rzeczywiste run IDs (jeśli dotyczy), ścieżki zrzutów i jawne ograniczenia. Nie zapisuj sekretów, cookies ani cudzych danych. `npm run verify` jest kontrolą pakietu, a nie zamiennikiem odbioru powyższego zachowania.

## Dowód maszynowy i review Cezara
